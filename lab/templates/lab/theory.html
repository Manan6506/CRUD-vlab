Keys and constraints

The primary key id uniquely identifies a row. Two properties follow from that, and you will verify both in the Exercises:

  • You never supply it. The database generates the next value on insert.
  • It is never reused. Delete row 5 and the next insert becomes row 6 — so a reference to row 5 held elsewhere can never silently point at a different student.

The UNIQUE constraint on email is a different kind of rule: it does not identify rows, it forbids duplicates. Try to insert a second student with an existing email and the database refuses the statement outright.

Two layers of checking

Steps 4 and 6 both reject bad data, but they are not the same thing:

  • Form validation runs in the application, before any SQL is sent. It produces friendly, per-field messages — "Phone number must be 7 to 15 digits".
  • Database constraints run inside the database and apply to every write, including ones from the REST API, the admin or a SQL console. They are what actually guarantees the data stays correct.

A well-built application has both. The form exists for the user's benefit; the constraint exists for the data's.

Why values are not pasted into the SQL

Throughout this lab the SQL is displayed with your values written inline, so it reads naturally. A real application must never build a statement that way — a value containing a quote character would change the meaning of the statement, which is the basis of an SQL injection attack. The ORM sends the statement and the values separately:

What is actually sent to the database
INSERT INTO students (name, email, phone) VALUES (?, ?, ?);
-- parameters: ['Asha Patil', 'asha.patil@example.com', '+919876543210']

Because the value never becomes part of the statement text, there is nothing an attacker can type that the database will execute.
