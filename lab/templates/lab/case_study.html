The scenario

The Computer Engineering department keeps a register of its students. Until recently it was a spreadsheet on one clerk's computer, used for three things: emailing notices, phoning a guardian in an emergency, and producing the attendance roll.

Over one semester the spreadsheet caused four separate problems.

  1. The same student entered twice

    Under two slightly different spellings of their name. They received every notice twice and appeared twice on the roll.

  2. A letter typed inside a phone number

    98765 4321O — with a capital O instead of a zero. Nobody noticed until an emergency call failed to connect.

  3. Two students given the same roll number

    After a sorting mishap. Their internal marks were swapped.

  4. A vacated roll number reissued

    A student who transferred out was deleted, and a new student later inherited their roll number — so an old entry in the marks register now pointed at the wrong person.

How the table design answers each problem

ProblemDesign decisionMechanism
The same student twice Email is declared UNIQUE, so a second row with the same address is refused by the database. UNIQUE constraint
A letter in a phone number Phone numbers are validated against a format rule before the row is saved. field validator
Two students sharing an identifier The identifier is generated by the database, not typed by a clerk, so a collision cannot occur. PRIMARY KEY
A reused identifier Deleted identifiers are retired permanently and never handed to a new row. AUTOINCREMENT

The resulting table

Those four decisions produce exactly the schema used in this experiment:

students
CREATE TABLE students (
    id     INTEGER      PRIMARY KEY AUTOINCREMENT,  -- generated, never reused
    name   VARCHAR(100) NOT NULL,
    email  VARCHAR(254) NOT NULL UNIQUE,            -- no duplicate students
    phone  VARCHAR(16)  NOT NULL                    -- format checked on write
);

Each CRUD operation maps onto something the clerk does: CREATE when a student joins, READ when the roll is printed, UPDATE when someone changes their phone number, and DELETE when a student transfers out.

Something to think about while you work. The fourth problem is the subtlest. Deleting a row is easy; what is hard is everything else in the system that still refers to it. When you reach the DELETE exercise, insert another row afterwards and watch which id it is given.
