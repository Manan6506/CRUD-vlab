What is CRUD?

Almost every application that stores information does only four things with it: it creates new records, reads records back, updates records that have changed, and deletes records that are no longer needed. These four are known collectively by the acronym CRUD.

The acronym is useful because it is the same everywhere. A college admission portal, a bank's account register and a social network's profile store differ enormously in scale and purpose, yet each is built from these four operations repeated over different tables. Learn them once on a small table and the pattern transfers directly.

Why a relational table?

A relational database stores data in tables of rows and columns. Each column has a declared type, and each row is one record. Crucially, the database can enforce constraints — rules it refuses to let you break, no matter what the application asks it to do.

That distinction is central to this experiment. Application code can and should check input before sending it, but the database is the last line of defence and will refuse a bad write even when the application forgets to. You will see both layers: a Django form rejecting a malformed phone number, and the database itself rejecting a duplicate email address.

What you will work with

The experiment uses a single table, students, holding four columns: an id that identifies each row, plus a name, email and phone. It is deliberately small, so nothing distracts from the operations themselves.

The Simulation section lets you perform each operation against this live table two ways — through forms, or by typing SQL and ORM commands into a terminal. Either way you see what you did, the SQL statement it corresponds to, and the Django ORM call that produced it. Every statement is recorded in a log, which is also what the Exercises section uses to check your work automatically.

About the technology. The experiment is built with Django, a Python web framework, over an SQLite database. You do not need to know Django to perform the experiment — but the Theory section explains how a request travels through it, because seeing that path is part of the point.
